## 1. Goal

Collapse the site's **two separate logins** into **one identity** on the shared convergence
project `noble-imprint-463519`, then consolidate everything you see once signed in
(account, notifications, admin console) into a single coherent surface.

Today there are two independent identities in two Google Cloud projects:

| | Admin / editor login (today) | Reader login (today) | After 1b |
|---|---|---|---|
| Project | `noble-imprint-website` | `noble-imprint-463519` | **`noble-imprint-463519` only** |
| SDK / entry | compat, `footer.ejs` | modular `readerApp` | modular `readerApp` (single) |
| authDomain | `resources.noblecollective.org` | `account.noblecollective.org` | `account.noblecollective.org` |
| Server trust | `__session` cookie via default admin app | client-only | `__session` cookie via a **463519** admin app |
| Powers | editing, suggestions, admin, notifications | highlights/notes/bookmarks/answers/settings | everything |

## 2. Why this is low-risk to admin functionality

**Every authorization and attribution path keys on `req.user.email`, never on the Firebase `uid`.**
Verified across the server:

- Edit roles / permissions → `firestore.getUserBookRole(req.user.email, …)` (`index.js`, `suggestion-routes.js`, `notification-routes.js`, `content.js`)
- Suggestions & comments → `authorEmail: req.user.email` (`suggestion-routes.js:255,270`)
- Notification prefs → `getNotificationPrefs(req.user.email)`
- Analytics attribution → `user_email: req.user.email` (`analytics.js:255`)
- Super-admin → hardcoded email compare `steve@noblecollective.org` (`auth.js:5,14`)

The email is the **same Google account** regardless of which project mints the token, so roles,
suggestion history, the admin console, notifications, and analytics keep working **untouched**.
No data migration: existing admins/editors simply re-sign-in once under 463519 (Steve already has a
463519 identity from reader testing).

**The only thing that changes is the authentication plumbing**, and its blast radius is
"can someone sign in," not "is content/data safe." It is fully testable locally and reversible
by config. That's why this is its own small phase rather than a risky rewrite.

## Part A — Unify the auth plumbing on 463519

### A1. Single front door
- `footer.ejs`: remove the compat `firebase.initializeApp({ projectId: 'noble-imprint-website', … })`
  block and the `auth.js` (compat) `loginWithGoogle()`/`logout()` path. The reader bundle's
  `readerApp` (modular, 463519, `authDomain: account.noblecollective.org`) becomes the **only**
  sign-in. It's already loaded site-wide (footer) after the site-wide-controls change.
- Keep the site's own `firebase-app-compat`/`auth-compat` script tags **only if** something else
  still needs them; audit `main.js`/`auth.js` first. Target: one auth SDK on the page.

### A2. Server session cookie on a 463519 admin app  *(the one real infra task)*
`/api/auth/session` (`index.js:415`) currently calls `auth.createSessionCookie(idToken)` and
`admin.auth().verifyIdToken(idToken)` on the **default** admin app (= noble-imprint-website).
The idToken will now come from **463519**, so both must run against a 463519-initialized app.

- Add a **named admin app** `auth463519 = admin.initializeApp({…}, 'auth463519')` used *only* for
  auth: `verifyIdToken`, `createSessionCookie`, `verifySessionCookie`.
- Keep the **default** admin app (noble-imprint-website) for **Firestore** (users, roles,
  suggestions) and everything else — that data does not move.
  → i.e. auth identity comes from 463519, application data stays in noble-imprint-website. Clean split.
- **Credentials — DECIDED: keyless impersonation (option 2).** `createSessionCookie` must *sign*, so
  the 463519 app needs signing authority on 463519. Chosen approach:
  - Init `auth463519` with `{ serviceAccountId: '<463519-firebase-adminsdk-sa>' }` and **no key**.
    The Admin SDK signs session cookies via the IAM Credentials `signBlob` API (not a local key).
  - One IAM grant: website Cloud Run runtime SA gets `roles/iam.serviceAccountTokenCreator` on that
    463519 SA. `verifyIdToken` needs no creds (public certs only).
  - **Why over a stored key:** the 2026-09-03 hardening deliberately dropped SA key files
    (`service-account-key.json` .dockerignore'd, prod on ADC, Secret Manager holds values not keys).
    Keyless keeps that posture: nothing long-lived to rotate/guard, auto-managed, consistent with
    the rest of prod. Tradeoff: one cross-project IAM grant + a tiny `signBlob` call per mint.
  - **Fallback** (only if the grant proves fiddly): 463519 SA key JSON in Secret Manager, used solely
    to init the named app. Self-contained but reintroduces a long-lived secret — avoid unless needed.
- `auth.js`: `createSessionCookie`/`verifySessionCookie` switch to the named app. `attachUser`
  (`auth.js:79-88`) is otherwise unchanged — it still decodes to `.email`.

### A3. OAuth / authorized domains on 463519
- Authorized domains already include `resources.noblecollective.org` and `account.noblecollective.org`
  (added in 1a / custom-auth-domain work). Confirm the Web OAuth client
  (`160156401404-ndlp…`) has JS origin `https://resources.noblecollective.org` and that the
  session flow (ID token → cookie) needs no new redirect URI (popup already works).

### A4. Client sign-in → server cookie bridge
- Reader `signIn()` (firebase.js) already does `signInWithPopup`. After success, POST the 463519
  **ID token** to `/api/auth/session` so the server mints `__session`. `signOut()` also POSTs
  `/api/auth/logout` and clears the client session. This makes the **client 463519 auth** and the
  **server session cookie** one and the same identity.
- `onUser` listener already drives the account icon; extend it to run the cookie bridge so a single
  sign-in lights up both reader features (client) and editor/admin access (server).

### A5. Dev / test path is unaffected
- `/api/auth/test-login` (dev-only, `index.js:449`) sets the `__dev_auth` cookie that `attachUser`
  recognizes — **no real token, no project dependency**. The entire Playwright suite keeps working.
- The reader E2E harness (`test-harness/`) uses the emulator seam (`?ncEmu=1`) — unaffected.

### A6. Gating & rollback
- Land behind a flag (e.g. `AUTH_UNIFIED=1`) so we can deploy dark and flip. If sign-in breaks,
  flip the flag back → the noble-imprint-website compat login returns. Snapshot the current
  `footer.ejs` auth block + OAuth client config before changing.

## Part B — Consolidate the signed-in UX

### B0. One account menu (kill the second sign-in)
Remove the server-rendered `partials/sidebar-auth.ejs` sign-in/links (the "2nd sign-in" Steve
flagged). The reader **account menu** (`nc-acct`, in `reader-userdata-entry.js`) becomes the single
place for identity + contextual links. This removes the duplication that unification makes redundant.

### B1. Coram-Deo-style interim sign-in popover
Steve likes CD's affordance: clicking the account icon while signed **out** shows a short intro
popover — *"Sign in to save your bookmarks, highlights, and notes across devices."* — with a
**Continue with Google** button, rather than firing the OAuth popup immediately. Implement as a
small `nc-menu`-styled popover anchored to the account icon; the button triggers `signIn()`.
(Today the icon calls `signIn()` directly; the tooltip already carries this copy.)

### B2. Role-aware links once signed in
Pass the server's role flags to the client so the menu/icons can be role-aware. Add a small
site-wide global in `footer.ejs` from `res.locals.user` (already available after `attachUser`):
```js
window.__NC_USER = { email, displayName, photoURL, isAdmin, isEditor };
// isEditor = has comment-suggest+ on any book (compute once, cache per request)
```
The reader bundle reads `__NC_USER` for role gating; the client 463519 auth listener remains the
source of truth for the live signed-in/out transition (they agree once unified).

### B3. Admin icon in the control cluster — DECIDED (Steve: yes, icon next to Settings)
Add a **shield/admin icon** to `.nc-side`, shown **only when `__NC_USER.isAdmin`**, linking to
`/admin`. Placement: **next to Settings**. Cluster becomes **Account · Settings · Admin · Notebook**.
Invisible to everyone who isn't an admin.

### B4. Notifications — keep it editor-accessible ⚠
**Caveat that reshapes Steve's proposal:** the Notifications page is **not admin-only** — it's open
to any signed-in user with `comment-suggest` role or higher on any book
(`notification-routes.js:8-9,27`). Burying it *inside* the admin console (admin-gated) would cut off
non-admin editors (manuscript-owners, contributors) who depend on mention/review notifications.

Reconciled design — **DECIDED (Steve approved):**
- **Add Notifications as a tab in the admin console** (for admins) — satisfies the "one console"
  instinct.
- **Also keep a "Notifications" row in the account menu** for anyone with `isEditor` (incl. admins),
  linking to the same page/settings. Non-admin editors keep access; admins get both entry points.
- Net: notifications settings has one implementation, two role-appropriate doorways. Nobody loses
  access. (If we later want it fully inside the console, we'd have to open a scoped, editor-only
  console view — out of scope here.)

### B5. Resulting signed-in surface
- **Signed out:** account icon → B1 intro popover → Google.
- **Signed in (reader only):** account menu = name/email · Notebook (already an icon) · Sign out.
- **Signed in (editor):** + "Notifications" menu row.
- **Signed in (admin):** + shield icon → `/admin` (with a Notifications tab inside).

## Risks & mitigations
- **Blast radius = login only.** No content/data write path changes; all attribution is email-keyed.
- **Cross-project signing (A2)** is the one genuine unknown → de-risk with option-1 (stored 463519 SA
  key) and a local end-to-end test before deploy.
- **Reversible** via `AUTH_UNIFIED` flag + snapshots of `footer.ejs` auth block and OAuth config.
- **Prod-auth change ⇒ explicit go-ahead required before deploy** (per standing rule); this plan is
  review-only.

## Decisions
1. **DECIDED — A2 credentials: keyless SA impersonation** (no stored key; matches the hardening
   posture). Stored-key is the documented fallback only if the IAM grant is troublesome.
2. **DECIDED — B4:** Notifications lives as a row in the **account menu** (the person-icon dropdown)
   for editors, plus a console tab for admins, so non-admin contributors don't lose it.
3. **DECIDED — B3: yes, shield icon next to Settings**, admins only. Cluster =
   Account · Settings · Admin · Notebook.
