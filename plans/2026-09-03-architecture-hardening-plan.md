# Noble Imprint Resource Website — Architecture Hardening Plan

_Created 2026-09-03. Source: whole-repo architecture review via six parallel review agents (deployment/CI, security, content-pipeline/data-safety, code/feature quality, testing/observability, analytics/email/integrations). Modeled on the Coram Deo hardening plan. This plan covers only the **meaningful** work; the nice-to-have/future backlog is listed at the end for the record but is out of scope here._

## Guiding split: what seriously helps vs. what's nice-to-have

**The test for "meaningful":** does it (a) prevent data loss or a prod outage, (b) stop a currently-live user-facing or security failure, or (c) lay a foundation that makes every future change safer? Everything else — pure refactors, latent-but-dormant issues, perf tuning at a scale we're not at — is deferred.

**Overall posture (context for the reader):** the app is **defensively written** where it counts — every Express route wraps async work in try/catch, there's a global error handler + `error.ejs` (no stack leak), client fetches degrade gracefully, and the content read path is genuinely well-insulated from GitHub/BigQuery/Firestore/Mailgun outages (stale-while-revalidate over a committed disk snapshot; analytics and email are fire-and-forget). The gaps are **not** in day-to-day rendering. They cluster in three places: **(1) a set of unauthenticated destructive/expensive endpoints, (2) no "is this snapshot sane?" floor between cache regeneration and persistence/commit, and (3) missing operational safety rails** (no CI gate, no health probe, no error alerting, no crash handlers). Two access-control bugs in the editor/suggestion surface round out the security work.

### ✅ Meaningful (this plan)

| # | Item | Why it's meaningful |
|---|------|---------------------|
| **S1** | Authenticate the open destructive/expensive endpoints (`/api/refresh`, `/api/refresh-audio`, `/api/cleanup-test-data`, `/api/content-tree`) | All four mount directly on `app` with **no guard** (`REFRESH_SECRET` referenced in deploy notes/CLAUDE.md **does not exist in the code**). `POST /api/refresh` invalidates all caches **and `github.clearDiskCache()` — deleting the outage fallback** — then forces a ~70-call rebuild. Anyone can loop it to drain the 5000/hr GitHub budget *and* strip the fallback → site 500s/blanks (remote DoS). `cleanup-test-data` batch-**deletes** Firestore data (bounded to Test Book, still public). `content-tree` leaks hidden/unpublished books. Flagged independently by 4 of 6 agents. |
| **S2** | Fail-closed shared secrets | `POST /api/notifications/send-daily-summary` guard is `if (schedulerKey && provided !== schedulerKey && !isAdmin)` — if `SCHEDULER_SECRET` is unset it **fails open** (any signed-in Google user triggers a batch email send). Same fail-open class to avoid when adding S1's secret. |
| **S3** | `filePath ⊂ bookPath` enforcement on suggestion create **and** accept | A `comment-suggest` user on Book A can POST a hunk whose `bookPath` is A (passes `canEdit`) but whose `filePath` targets **another** book's file. Authz on accept checks `hunk.bookPath` only; the commit writes to `hunk.filePath`. A reviewer accepting → arbitrary content committed to a file the author has no rights to. Privilege-escalation / content-integrity. |
| **S4** | `.dockerignore` the SA key + fix secret wiring/doc | `service-account-key.json` (live GCP private key) is gitignored but **not dockerignored**; the README-documented **manual** `docker build` bakes it into the pushed image (credential leak; runtime uses ADC and doesn't need it). Separately, `deploy.yml` sets no secrets and README claims prod reads `.env` "from Secret Manager" — not how the container actually gets them; document/pin the real wiring. |
| **S5** | Per-book authorization on suggestion **read** endpoints + XSS floor | `/file-version`, `/suggestion-count`, `/presence`, `/file`, `/history` require *any* signed-in user (self-serve Google sign-in) with **no per-book role check** → anyone can read pending suggestions/comments/editor identities for any book by path. Plus `markdown-it html:true` with no sanitization: raw `<script>` in a suggestion `newText` (server does not enforce "text-only") renders to all visitors if an admin accepts it — admin review is the only barrier today. |
| **S6** | IP-hash salt fail-fast | If `ANALYTICS_IP_SALT` is unset, IPs hash with the public constant `'dev-unsalted-change-me'` → `ip_hash` reversible over the IPv4 space, defeating the stated privacy guarantee. Fail-fast/disable ingestion if the default salt is in use in prod. |
| **R1** | Verify + enable Firestore backups (scheduled + PITR) — _the recovery floor under all the data-safety work below_ | **The safety net under everything Firestore holds** — and Firestore has **no automated backups by default**. Two collections are effectively irreplaceable and are **not** in git: `users` (the entire per-book roles/permissions model) and `contentRegistry` (the random, forever `content_id`↔path map — lose it and **all historical analytics is orphaned permanently**, unregenerable). Also `suggestions`/`comments`/`replies`/`notifications` (editorial work). This lands harder because the review found an **unauthenticated `/api/cleanup-test-data`** doing Firestore `batch.delete()` (S1) and the registry `inherit()` path **hard-deleting** docs on a degraded tree (DS4) — i.e. live paths to wrongly delete data with, currently, unknown recoverability. Content itself (books/sessions/bible) is well-protected — it lives in git with full history, so this is specifically a Firestore gap. Verified/enabled in Phase 0. |
| **DS1** | Content-tree floor guard before cache write | `rebuildContentTree` writes whatever it built to memory **and disk unconditionally**; the book/session loaders swallow all errors → empties. A mid-rebuild API degradation yields a valid-shaped but content-poor tree (`{series:[]}` or books with 0 sessions) that **overwrites the good disk snapshot** (the outage floor). Single worst data-safety risk: ships a blank/missing-content live site. |
| **DS2** | Nightly `refresh-cache.yml` validation before commit (+ don't `rm` first) | The job regenerates then blind-commits, gated only on `git diff --staged --quiet`; it can't tell "changed" from "degraded." The bible step does `rm -f .bible-cache/*.json` **before** rebuilding, and `loadBibles()` never throws on a per-translation fetch failure → a rate-limited run **commits the deletion** of the bible snapshot and exits 0; next deploy ships without it. Validate (book-count floor, all bible files present + parse to ≥N verses) and temp-swap-on-success before commit. |
| **DS3** | `warmDiskCache` / `bible.reload()` fail-loud + rebuild-then-swap | `warmDiskCache` swallows its own rebuild error and returns normally, so the workflow's `.catch(exit 1)` **can never fire** (defeats DS2's gate). `bible.reload()` (fired after any BSB-sync commit) deletes the disk snapshot **before** confirming a good re-fetch → a rate-limited moment leaves the reader serving *no verses* until restart. Both: build into temp/memory, verify non-empty, then swap; reject on failure. |
| **DS4** | Content-registry orphan guard on degraded trees | `syncTree` treats any registered path absent from the current tree as an orphan; `inherit()` then **deletes** the old Firestore doc and reassigns its `content_id`. Fed a degraded tree (DS1), live books look "disappeared" → a new path can steal their analytics identity and the original doc is deleted. Gate `syncTree` on a tree that passed DS1's floor; skip orphan recompute on a sharp path-count drop. (Low probability, but coupled to DS1 and destructive.) |
| **CI1** | CI quality gate before deploy | `deploy.yml` pushes straight to prod: **no test, lint, or build step**. `npm run test:unit` (134 hermetic cases) and `build:editor` exist but never run in CI, and the CodeMirror bundle is committed, not built — a stale bundle can ship. Add a `test` job (`npm ci` → `test:unit`, rebuild bundle + `git diff --exit-code`) that `deploy` `needs:`. |
| **CI2** | Per-commit image tags + config pinning + rollback doc | `:latest`-only image (no immutable per-SHA tag, no written rollback runbook). `deploy.yml` pins only `--min-instances=0`; memory/cpu/**max-instances**/concurrency/timeout live only in the deployed service (drift-prone, lost on recreate). No `--max-instances` = unbounded fan-out into the shared GitHub budget under a spike. |
| **OB1** | `/healthz` readiness route + Cloud Run probe | Server `app.listen()`s before Bibles/content load "so the health check passes"; Cloud Run's default probe is a TCP connect → passes the instant the socket opens. A fully-broken content pipeline (GitHub down + empty cache) serves 500s while the container reports **healthy**. Add a `/healthz` that's 200 only when the tree is servable + Bibles loaded; wire `--startup-probe`/liveness. |
| **OB2** | Error alerting + nightly-job failure alert | Only error surface is `console.error` → plain Cloud Logging. No Sentry-equivalent, no log-based alert. **Today Steve learns prod is erroring only from a user report or by manually reading logs.** `refresh-cache.yml` failure has no notify step (GitHub emails only the last committer — a bot). Add a log-based alert on `severity>=ERROR` + an `if: failure()` notify on the nightly job. |
| **OB3** | Process-level crash handlers | No `unhandledRejection` / `uncaughtException` handlers anywhere in `src/`. One stray rejected promise (Node 15+) terminates the process, dropping **all** concurrent in-flight requests on that instance. Cheap insurance; combines with OB1/OB2 to make crashes visible + recoverable. |

### 🟨 Nice-to-have / future (NOT in this plan — see backlog at bottom)
Analytics `collect` rate-limiting; arbitrary-recipient email validation; unbounded notifications collection growth + O(all-history) today-check query; `helmet`/security headers + general rate limiting; constant-time secret compares; dedupe the anchor-resolution block (×5); structured/leveled logger; malformed-`@include` render-boundary fallback; `Promise.all` the serial per-book role reads on `/notifications`; scoped audio cache invalidation (stop nuking the whole cache on `refresh-audio`); Dockerfile hardening (digest pin, `USER node`, `HEALTHCHECK`); directory-listing/`data.truncated` truncation guards; BigQuery retry/`SIGTERM` flush; `contentIdFor` off the render hot path; `geoip-country` bump cadence; Mailgun startup warning + bounce handling; `references.json`↔USFM reconciliation report; large-file/function refactors (`getSessionPageData`, `editor.js`, `admin.js`).

Rationale for deferring the notable ones:
- **Analytics rate-limiting + email-recipient validation** are real abuse/cost levers but bounded at current traffic; pull forward as a small Phase 6 if traffic grows or costs show up.
- **helmet / general rate limiting / notifications growth / FK-style indexes** are scale hardening we don't need at current volume.
- **Refactors & dormant issues** carry no active failure — the anchor-resolution dedup is the most defensible (bug-prone area) and is the first to promote.

## Execution plan for the meaningful work

Six phases, ordered by risk-reduction-per-effort and dependency. Phases 0–2 are the "sleep at night" batch. **Nothing here deploys without Steve's explicit go-ahead** (standing rule); each phase ends with a verification step, and per standing rules I'll present options rather than pick unilaterally where there's a real choice.

### Phase 0 — Verify the truth (ops, no code; do first)
Establishes reality before we trust anything downstream. Deliverable: a short "prod truth" note appended to this file.
- **R1 — Firestore backups (do this first; it's the recovery floor under everything else):** confirm whether a **scheduled backup** policy and **PITR** are enabled on the default database:
  - `gcloud firestore backups schedules list --database='(default)' --project=noble-imprint-website`
  - `gcloud firestore databases describe --database='(default)' --project=noble-imprint-website --format='value(pointInTimeRecoveryEnablement)'`
  - If both are off → **stop and fix that first** (enable a daily scheduled backup with retention + PITR; ~5 min). Note: BigQuery `analytics.events` has 7-day time-travel (lower stakes); GCS audio/offline assets are regenerable. The GitHub content repo is git-versioned (no action).
- **Cloud Run service config:** dump `gcloud run services describe resource-website` — record current memory/cpu/max-instances/concurrency/timeout (so CI2 pins the *known-good* values, not guesses), and **how secrets are actually set** (plain `--set-env-vars` vs `--set-secrets` from Secret Manager). README claims `.env`-from-Secret-Manager; confirm.
- **Which secrets are actually set in prod:** critically `ANALYTICS_IP_SALT` (is S6 live now?) and `SCHEDULER_SECRET` (is S2 live-exploitable now?). Also confirm `GITHUB_TOKEN`/App scope (Contents R/W on the one repo).
- **Recovery floor:** confirm there's a recent good committed cache snapshot (content tree + `.bible-cache`) to restore from if a degraded one shipped.
- If the SA key is confirmed unused at runtime (ADC), note it so S4's dockerignore is safe.

### Phase 1 — Lock the open doors (small, urgent)
Self-contained, high-value, mostly a few lines each. TDD where a unit test is cheap.
- **S1:** add a shared-secret (or `requireAdmin`) gate to `/api/refresh`, `/api/refresh-audio`, `/api/cleanup-test-data`; apply `filterContentTree(tree, req.user)` (or auth) to `/api/content-tree`. **Introduce the `REFRESH_SECRET` that deploy notes already assume**, wired to the deploy/audiobook workflows. Make `/api/refresh` never call `clearDiskCache()` from a public/unauthenticated path. Keep the test suite's `?scope=files` path behind the auth it can already present.
- **S2:** make `SCHEDULER_SECRET` mandatory — deny when unset (fail closed), not allow.
- **S4:** add `service-account-key.json` (and `*.json` scoped, `.git`, `tests/`, `plans/`) to `.dockerignore`; correct the README secret table.
- **S6:** fail-fast (or disable analytics ingestion) if `ANALYTICS_IP_SALT` is the default constant in production.
- **Verify:** unauthenticated calls to the four endpoints now 401/403; a valid secret still works; `docker build` no longer contains the key (`docker history`/inspect); with salt unset in a prod-like env the app refuses to hash with the default.

### Phase 2 — Data-safety floor guards (catastrophe prevention, TDD)
The three-angles-on-one-gap batch: **nothing may persist/commit a degraded snapshot.**
- **DS1 (floor guard):** _Write the failing test first_ — feed `rebuildContentTree` a degraded build (empty series / a book with 0 sessions that previously had some) and assert it **keeps the old snapshot** and does not overwrite disk. Then implement a single `isTreeSane(newTree, prevSnapshot)` check (e.g. `series.length>0`, book count ≥ ~90% of prior, no previously-populated book dropping to 0 sessions) used before `cache.set`/`writeFileSync`; on failure keep the old snapshot + log loudly.
- **DS3 (fail-loud):** make `warmDiskCache` and the per-translation `loadBibles` path **reject/return a failure status** instead of swallowing, so DS2's workflow gate can actually fire. Change `bible.reload()` and the bible cache build to **rebuild-then-swap** (verify non-empty parse before deleting/overwriting the disk snapshot).
- **DS2 (nightly validation):** in `refresh-cache.yml`, regenerate to temp, **validate before commit** (content tree parses + book-count floor; all `.bible-cache/{bsb,kjv}-v1.json` present and parse to ≥N verses), and only then swap + commit; never `rm` before a verified rebuild. Reuse DS1's `isTreeSane`.
- **DS4 (registry guard):** gate `syncTree`'s orphan recomputation on a tree that passed DS1's floor; skip when `currentPaths.size` drops sharply vs. the last good sync; prefer soft-delete over hard `doc().delete()` in `inherit()`.
- **Verify:** `npm run test:unit` green; locally simulate a degraded rebuild → disk snapshot untouched, site still serves; simulate a rate-limited nightly run → job fails **without** committing a deletion.

### Phase 3 — CI/CD & deploy safety
- **CI1:** add a `test` job to `deploy.yml` (or a `ci.yml` on PR + push): `npm ci`, `npm run test:unit`, `npm run build:editor` + `git diff --exit-code src/public/js/codemirror-bundle.js` (fail if the committed bundle is stale). `deploy` `needs:` it, so a red gate blocks prod; PRs run the gate but don't deploy.
- **CI2:** tag the image `:$GITHUB_SHA` in addition to `:latest`, deploy the SHA tag; pin `--memory`/`--cpu`/`--max-instances`/`--concurrency`/`--timeout` (from Phase-0 known-good values) in the deploy step; add a "Rollback" section to README/CLAUDE.md (`gcloud run services update-traffic --to-revisions=…`).
- **S5-adjacent secret wiring:** if Phase 0 found secrets set as plain env vars, move `GITHUB_TOKEN`/`REFRESH_SECRET`/`ANALYTICS_IP_SALT`/etc. to `--set-secrets` from Secret Manager and correct the README.
- **Verify:** a PR with a deliberate failing test / stale bundle is blocked; a normal deploy produces a SHA-tagged image and preserves memory/max-instances; secrets no longer appear in `run services describe` plaintext.

### Phase 4 — Access-control hardening (editor/suggestion surface)
- **S3:** on suggestion create AND accept, assert `filePath.startsWith(bookPath + '/')` (re-derive/validate on accept — don't trust the stored value).
- **S5:** add a `canView(req.user.email, bookPath)` check (deriving `bookPath` from `filePath`, as `/content` already does) to `/file-version`, `/suggestion-count`, `/presence`, `/file`, `/history`. Then close the XSS floor: run rendered HTML through a sanitizer for the reading view **or** strip raw-HTML tokens from suggestion `newText` server-side (so admin review isn't the only barrier).
- **Verify:** a hunk whose `filePath` escapes its `bookPath` is rejected at both create and accept; a signed-in user with no role on Book X gets 403 on its suggestion reads; a `<script>` in a suggestion is neutralized in the rendered reading view.

### Phase 5 — Observability & resilience
- **OB1:** add `GET /healthz` returning 200 only when the content tree is servable + Bibles loaded; wire `--startup-probe`/liveness in `deploy.yml`; add a post-deploy smoke `curl`.
- **OB3:** add `process.on('unhandledRejection'/'uncaughtException')` handlers that log with context (and exit on uncaught so Cloud Run restarts cleanly).
- **OB2:** add a Cloud Logging log-based alert on `severity>=ERROR` (or on the global handler's log line) → email/Slack; add an `if: failure()` notify step to `refresh-cache.yml`. (Full Sentry stays in the backlog; a thin leveled logger with request-ids can start here.)
- **Verify:** kill GitHub access + clear cache locally → `/healthz` reports unhealthy (probe would fail the revision) instead of serving silent 500s; a forced unhandled rejection is logged, not silent; a deliberately failed nightly run notifies.

### Phase 6 — Abuse/cost & content robustness (small, optional)
- Rate-limit `/api/analytics/collect` (+ a small body/event cap) to cap BigQuery streaming-insert cost and dashboard pollution.
- Validate `mentionedUsers` email addresses against known users before sending (stop arbitrary-recipient mail via your Mailgun domain).
- Catch `IncludeError` at the session render boundary → render the raw directive + a visible warning banner instead of a 500 (one bad `@include` param currently darks a published page).
- Bound the notifications "today" check (`where(createdAt >= today).limit(1)` + index) and add a prune/TTL — promote from backlog if editing volume grows.
